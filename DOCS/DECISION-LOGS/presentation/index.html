Data model

How should Programme, Route and Bus relate?

Decision 01 / 08

This defines the entire capacity engine — how seats are counted, where "available seats" comes from, and how far the schema can stretch before it needs rework.

A

One route = one bus (1:1). Each route has exactly one bus and one capacity figure, tracked directly on the route.

Effort · LowReversibility · LowScalability · Single bus per route only

B

A route can have multiple buses. A popular route is assigned several buses; capacity is their sum.

Effort · MediumReversibility · MediumScalability · Grows with route demand

C

Buses attach to the programme directly. Routes become pickup labels only, not capacity holders.

Effort · LowReversibility · LowScalability · Loses per-route control
Touches: DATABASE schema, capacity engine, seat-count reporting.
Technology stack

What should the build actually run on?

Decision 02 / 08

The PRD recommends an all-TypeScript stack; prior project work leans Python. This choice sets the repository layout, hosting, and who can maintain it later.

A

Next.js + Supabase. API routes, Postgres, auth and realtime in one TypeScript codebase, hosted on Vercel.

Effort · Low (1 codebase)Reversibility · LowScalability · Scales via managed tiers

B

FastAPI + React + Postgres. Python backend, React PWA frontend, self-managed or managed Postgres.

Effort · Medium (2 codebases)Reversibility · LowScalability · Full infra control

C

Next.js frontend + FastAPI backend. TypeScript on the client, Python on the API.

Effort · High (2 languages)Reversibility · LowScalability · Most flexible, most upkeep
Touches: BACKEND, FRONTEND, DATABASE, hosting cost, who can contribute later.
Booking integrity

How are seats protected during checkout?

Decision 03 / 08

The last-seat problem: two members try to book the final seat on a route at the same moment, or one pays and abandons checkout.

A

TTL hold on booking start. Seat is reserved for a short window once checkout begins; released automatically if payment isn't completed.

Effort · MediumReversibility · MediumScalability · Holds under concurrent load

B

Decrement only on payment success. Seat stays bookable until payment clears.

Effort · LowReversibility · HighScalability · Breaks down under concurrent demand

C

Decrement on booking, manual cleanup. Seat taken immediately; abandoned ones freed by a Marshal or Admin.

Effort · LowReversibility · HighScalability · More admin work as volume grows
Touches: capacity engine, payment webhook handling, reporting accuracy.
Scheduling

How is the Friday-6pm booking window handled?

Decision 04 / 08

Sunday-service booking opens Friday 6pm (BRD requirement 6) and should close once a route is full. Who or what enforces that timing?

A

Scheduler / cron component. A scheduled job opens and closes booking windows automatically per programme configuration.

Effort · MediumReversibility · MediumScalability · Handles many programmes at once

B

On-demand time check. No scheduler — availability is computed from timestamps whenever a member loads the page.

Effort · LowReversibility · HighScalability · Fine, but no proactive alerts

C

Manual admin toggle. Admin opens and closes booking by hand from the dashboard.

Effort · LowReversibility · HighScalability · Relies on someone remembering
Touches: BACKEND job runner (if any), member-facing availability display, notification timing.
Operations

How is a Marshal reassigned mid-programme?

Decision 05 / 08

Not specified in the BRD: a Marshal assigned to a route becomes unavailable after bookings have already started coming in.

A

Admin-triggered reassignment. Admin manually reassigns the route; notifications re-scope to the new Marshal.

Effort · LowReversibility · HighScalability · Fine with few concurrent routes

B

Marshal self-release + claim pool. A Marshal releases a route; any eligible Marshal can claim it.

Effort · MediumReversibility · MediumScalability · Scales with more Marshals/routes

C

No formal flow. Handled by phone call / word of mouth, outside the system.

Effort · NoneReversibility · HighScalability · Breaks down past a few routes
Touches: notification engine, route-scoped access control, Marshal dashboard.
Payments

How automated should refunds be?

Decision 06 / 08

BRD Section 16 requires a refund policy for cancelled paid bookings, but leaves the execution mechanism open.

A

Full-auto refund via Paystack API. Cancellation triggers an automatic refund call, status tracked end to end.

Effort · MediumReversibility · MediumScalability · No finance bottleneck at volume

B

Flagged for manual finance review. System records the refund is owed; a person approves and triggers it.

Effort · LowReversibility · HighScalability · Review queue grows with volume

C

Fully manual. Bank transfer reconciliation outside the app, same as today.

Effort · LowReversibility · HighScalability · Does not scale past a handful/month
Touches: payment status machine, audit trail, Journey C (member cancellation).
Registration

How are duplicate registrations handled?

Decision 07 / 08

BRD Section 6 asks the system to "avoid unnecessary duplicate registrations" without defining the match rule — e.g. same person, different phone number.

A

Auto-merge on email / Google ID match. Matching identity signals merge records automatically.

Effort · MediumReversibility · Low (merges are hard to undo)Scalability · Clean records at any member count

B

Flag for admin review, no auto-merge. Possible duplicates are surfaced; a person decides.

Effort · LowReversibility · HighScalability · Review queue grows with signups

C

Block re-registration outright. A detected match prevents a new account from being created.

Effort · LowReversibility · HighScalability · Simple, risks locking out real members
Touches: registration flow, member data integrity, reporting (first-time vs returning).
Reporting

How granular should no-show tracking be?

Decision 08 / 08

BRD Section 17 separates "no-shows" in reports, but the booking lifecycle (Section 12) doesn't say whether No-show is its own tracked state.

A

First-class state in the lifecycle. No-show becomes a tracked terminal state, distinct from Confirmed.

Effort · MediumReversibility · LowScalability · Enables demand forecasting

B

Informal Marshal note. Recorded as a comment, not a structured state.

Effort · LowReversibility · HighScalability · Reporting stays shallow

C

No tracking. Absences are not recorded at all.

Effort · NoneReversibility · HighScalability · No attendance pattern data, ever
Touches: state machine, reporting engine, future capacity planning.
